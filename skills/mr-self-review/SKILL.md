# MR и self-review

Скилл имеет смысл только вместе с правками по задаче: он оформляет уже сделанную работу и каждую следующую
итерацию правок. Без изменений в ветке запускать нечего.

## 1. Отдельный worktree

В основном checkout могут параллельно работать другие сессии и сам пользователь.

- Перед первой правкой посмотреть `git worktree list`. Есть worktree этого тикета – работать в нем.
- Нет – `git fetch`, затем `git worktree add ../<repo>-<TICKET> -b <ветка> origin/<основная ветка>`.
- В worktree нужно собирать или запускать сервисы, а сборка с нуля долгая (сотни проектов, `npm ci`) – взять
  артефакты из уже собранного основного checkout:
  1. Правки ветки закоммитить: копирование затрет рабочую копию worktree.
  2. Оценить размер: `robocopy <main> NUL /L /E /BYTES /NFL /NDL /NJH`. Свободно меньше размера плюс 10 ГБ – спросить
     пользователя до копирования.
  3. `robocopy <main> <worktree> /MIR /XD <main>\.git <папки деплоя и логов> /XF .git`: `.git`-файл worktree остается.
  4. В worktree `git reset --hard <ветка>` и `git clean -fd`: убирает чужие правки основного checkout, а игнорируемые
     `bin`, `obj`, `node_modules` остаются.
- Имя ветки – `<логин>/<тикет>-<коротко>`, например `ivanov/proj-123-short-name`. Логин – локальная
  часть `git config user.email`. Регистр тикета – как у большинства слитых веток:
  `git log origin/<основная ветка> --merges -40 --format=%s`.
- Ветка пользователя без `<логин>/` – предложить переименовать: запушить под новым именем, удалить старую
  на remote, у локальной поправить upstream. У открытого MR исходную ветку не сменить – нужен новый MR
  и закрытие старого, поэтому такую ветку переименовывать только с явного согласия.
- В основном checkout ничего не менять: не переключать ветку, не делать stash, не коммитить, не запускать сборку,
  которая пишет в рабочую копию. Читать можно.
- Каждая команда идет с `cd <worktree>` или абсолютными путями: shell между вызовами возвращается в основной checkout.

## 2. Коммиты итераций self-review

- Первый коммит по задаче – обычный, по правилам проекта.
- Каждый следующий коммит с правками по замечаниям помечается номером итерации в конце заголовка:
  `<type>(<scope>): <что поправлено> (self-review N)`.
- N = число коммитов с `(self-review` в `origin/<основная ветка>..HEAD` плюс один:
  `git log --oneline origin/master..HEAD --grep="(self-review"`.
- В теле – по строке на замечание: что изменилось. Ссылка на тикет и подпись – по правилам проекта.
- Коммиты по-русски, но в заголовке именно «self-review», не «ревью».
- Пушить и создавать MR – только после согласия пользователя. Перед пушем – rebase на свежий master.
- Состояние ветки на сервере – только по свежему `git fetch`. Перед пушем сравнить `git diff origin/<ветка> HEAD`:
  пусто – не пушить (новые хеши без новых файлов только перезапускают CI), выровнять локальную ветку по серверной.

## Чек-лист self-review диффа

Сначала вызвать скилл `mattpocock-skills:code-review` с точкой отсчета `origin/<основная ветка>`: он проверяет
дифф на соответствие тикету (лишнее и недоделанное) и на стандарты репозитория и типовые запахи (дублирование,
лишние абстракции). Его находки разобрать, затем пройти по пунктам ниже – их он не знает:

- Чужие правки в дифф не включать.
- Нет захардкоженных констант и имён: вынести в настройки; общую модель расширять
  свойством интерфейса со значением по умолчанию.
- Предпочитать встроенное в .NET ручным циклам и трюкам.
- Комментарии: 1–2 фразы «почему» у каждого неочевидного изменения, во всех аналогичных местах. Шумные – убрать.
- Ошибки: явное исключение с понятным текстом, без лишних деталей реализации.
- Паритет с аналогами (доки, examples), как у похожих функций.
- В доках существующий текст не править – добавлять рядом.
- Возможный «замысел» проверить по истории: замысел – комментарий, баг – TODO с комментарием.
- Тесты читаемы, перезапущены на текущем коде. Есть тесты на новые ветки логики.
- Форматтер – только на изменённых файлах.

## 3. Описание MR

Создать MR предложить сразу после первого коммита (`glab mr create` или `gh pr create`, по remote), не дожидаясь
конца работы. Перед созданием проверить, нет ли уже MR на эту ветку. Каждая итерация обновляет описание. Если у `glab` нет прав (403 `insufficient_granular_scope`),
MR на GitLab создается пушем: `git push -o merge_request.create -o merge_request.target=<base>
-o merge_request.title="<заголовок>" origin <branch>`, описание потом вставить в веб-интерфейсе.

Описание короткое – два абзаца, без заголовков, около 400 символов своего текста:

```markdown
<Одно предложение: что сделано и для кого заметно.> [<тикет>](<ссылка>).

Проверено <на чем: экран, запрос, входные данные одной строкой>: master – <что видно>, ветка – <фактический результат>.

<шаблон MR проекта, если есть (.gitlab/merge_request_templates), без изменений>
```

- Детали реализации, файлы и тесты в описание не писать. Отдельный документ для ревьюера не делать: ревьюят
  в том числе роботы, им хватает диффа.
- «Проверено» – только реально выполненная проверка (по скиллу ручной проверки проекта, если он есть) с фактическим результатом. Не проверял руками –
  так и написать, с причиной. Дописывать сразу после проверки, не дожидаясь просьбы.
- Если `glab` не читает MR (403), описание можно прочитать и обновить через GitLab API из встроенного браузера,
  где пользователь залогинен: `fetch('/api/v4/projects/<group%2Fproject>/merge_requests/<iid>')`, для PUT –
  заголовок `X-CSRF-Token` из `meta[name=csrf-token]`.
- Перед правкой описания найти MR по текущей ветке (`source_branch` = `git branch --show-current`, state opened),
  а не по номеру из памяти: после переименования ветки создается новый MR, старый закрывается.
